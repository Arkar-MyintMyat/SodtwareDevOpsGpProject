01

Why anyone cares about this

Every secure connection starts with two strangers agreeing on a secret key. The mathematics that makes that safe is exactly the mathematics a quantum computer breaks.

How keys work today

When your browser reaches a bank, the two sides have never met and share no password, yet they need the same key to encrypt the conversation. Public-key cryptography gets them one: the bank publishes a public key, keeps a private key, and the two sides derive a shared secret that an eavesdropper cannot reconstruct.

Its safety rests on two problems being too slow to compute — factoring very large numbers (RSA) and discrete logarithms on elliptic curves (ECDH). On ordinary hardware both would take longer than the age of the universe.

Why that stops working

In 1994 Peter Shor published an algorithm that solves precisely those two problems efficiently — on a quantum computer. Not weakens them. Breaks them. No machine large enough exists yet, and credible estimates range from ten to thirty-plus years.

So why migrate now?

Because of harvest now, decrypt later. An attacker can record encrypted traffic today, store it cheaply, and decrypt it in 2045 once the hardware exists. If the data still matters then — medical records, industrial designs, building-access keys — it is already lost. Recording costs almost nothing.

That is why NIST ran a decade-long competition and standardised the winner in August 2024 as FIPS 203: ML-KEM, known during the competition as Kyber. Governments are now publishing migration deadlines. This project is a miniature of work that thousands of organisations started this year.

02

What ML-KEM actually does

ML-KEM is a key encapsulation mechanism: three functions that leave two parties holding the same 32 random bytes.

FunctionRun byWhat comes out
keygen()ReceiverA public key and a private key
encaps(pk)SenderA ciphertext and a shared secret
decaps(sk, ct)ReceiverThe same shared secret

Read the middle row twice, because it is the whole idea. The sender does not choose a secret and send it. The sender runs one function that produces a random secret and a ciphertext. Whoever holds the private key recovers that same secret from the ciphertext. Everyone else gets nothing.

An analogy: you post someone a magic box. The act of locking it shows you a random number. Only their key opens the box, and inside is the same number. An interceptor holding the box learns nothing at all.

Why “lattice”

ML-KEM’s hard problem is Module Learning With Errors: recovering hidden values from many noisy linear equations. Geometrically it is finding the nearest point in a grid — a lattice — in hundreds of dimensions. Shor’s algorithm does not help, and no efficient quantum attack is known.

Our brief is explicit that we do not need this in depth. “A different hard problem that quantum computers don’t crack” is the required level.

The part that actually shapes our project: size

ML-KEM keys and ciphertexts are roughly 37 times larger than their elliptic-curve equivalents. On a web server nobody notices. On a sensor with a few kilobytes of RAM, this is the entire problem.

03

The system we’re modernising

Three components in the standard edge–cloud shape used by real industrial deployments. All three run today.

ComponentPathRole
Legacy devicelegacy_device/Simulates an Arduino-class sensor node. Reads temperature and humidity, sends one encrypted frame every two seconds, retries forever if the link drops.
Edge gatewayedge_gateway/Accepts many device connections on TCP 9000, decrypts and validates frames, rejects replayed sequence numbers, forwards readings onward.
Cloud servicecloud_service/FastAPI app. Ingests readings, exposes /health and read APIs, self-documents at /docs.

The wire format is deliberately crude — one newline-terminated ASCII line carrying a hex IV and ciphertext, wrapping a pipe-delimited record:

DEV|dev-001|1|21.50|44.20|12

…that is record type, device id, sequence number, °C, %RH, and uptime in seconds.

The critical property of the device is not that it is old. It is that it cannot be changed: thousands are installed in walls and on poles, there is no update mechanism, and replacing them costs more than the project. Every real modernisation has something like this in it.

04

The flaws are the assignment

Our baseline has eight documented weaknesses. None are accidents — together they are the backlog.

Cryptographic

01
No key establishment at allOne AES key, hardcoded in firmware, shared by the entire fleet, never rotated. Extract it from one device and you can read every device’s traffic forever. This is the “outdated key-establishment mechanism” the brief refers to — the thing ML-KEM replaces.
02
Unauthenticated encryptionAES-CBC hides content but does not prove it was unmodified. An attacker flipping bits produces garbage indistinguishable from a transmission error — the gateway genuinely cannot tell which it is seeing.
03
Static gateway tokenOne fixed string authenticates the gateway to the cloud. Anyone who learns it can inject fake telemetry — demonstrable by hand in /docs in about thirty seconds.
04
No transport security to the cloudPlain HTTP on the one hop that crosses untrusted network.

Operational

05
No store-and-forwardReadings are dropped, not queued, when the cloud is unreachable.
06
In-memory storage onlyA cloud restart erases every reading ever received.
07
No tests, CI, containers or metricsNothing verifies a change, and nothing reports on the running system.
08
Coupled deployablesThe gateway imports its protocol code from the device package, so two independently deployable services share one module.

The course is Software Development, Maintenance & Operations. Maintenance means improving a system you inherited and did not design — which cannot be practised on a greenfield project. Hence a flawed starting point, on purpose.

05

The 256-byte wall

Put two numbers side by side and the whole design follows: ML-KEM-768 needs 1184 bytes for a public key, and our device has a 256-byte buffer.

ML-KEM physically cannot run on the device. Not “would be slow” — it does not fit in memory. Most groups will assert something like this. We have it as a measured number in the code, beside a real frame measured at 98 bytes, which turns an opinion into evidence.

So we terminate post-quantum crypto at the gateway

The gateway becomes a crypto-translating proxy: legacy AES towards the devices, ML-KEM towards the cloud. The long-haul link becomes quantum-safe; the short local hop stays legacy and is documented as accepted residual risk with a written justification. This is what real deployments do. It is the correct answer, not a compromise.

Migration and fallback, as code

The gateway and cloud will negotiate which cryptography to use, which turns our migration strategy into something testable rather than something described:

legacy-rsa

Old behaviour, for gateways not yet upgraded. Our fallback path.

mlkem768

Pure post-quantum key establishment.

hybrid-x25519-mlkem768

The realistic answer. Classical and post-quantum combined, so you are only broken if both fail. Currently what NIST and the IETF recommend — and an easy citation for the report.

Because negotiation is code, we can write a test that forces a downgrade and proves the fallback works. That is far stronger than a paragraph claiming it would.

The transferable lesson: crypto-agility

The original system’s real problem is not that its cryptography is old. It is that the algorithm was welded into the code, so changing it means touching everything. Our job is to build a layer where the algorithm is a choice. Then the next migration — and there will be one — is a configuration change.

06

The baseline, measured

Think of it as the before photograph. We are about to change the cryptography, and somebody will ask what that cost. Without a measurement taken now, we could only answer with a number that compares to nothing.

So we measured the legacy system while it was still the legacy system, and we will re-run the identical script afterwards. The difference is the answer. Baseline analysis is also one of the things the brief asks for by name:

The brief asks forWhere it is
“Understand and document the initial architecture”This page, and README.md
“Run the system”Three services, verified end to end
“Establish baseline tests”58 tests in tests/
“…and measurements”tools/baseline.py → dated JSON

Step 1 — how big is one message?

Take one fixed example reading and measure it at every stage. The text DEV|dev-001|1|21.50|44.20|12 is 28 bytes; by the time it reaches the wire it is 98. Those extra 70 bytes are worth understanding, because they are what leaves the device only 158 bytes of headroom.

Step 2 — what does the key exchange cost?

This is the most important measurement and the most surprising. For the legacy system the answer is zero: zero bytes, zero round trips, zero milliseconds.

That is not a broken measurement. The zero is the finding. The legacy system does not agree on a key at all — the key is written into the firmware at the factory. Nothing is negotiated, nothing is sent, nothing rotates. A door with no lock also opens very quickly.

The 2272 bytes are the 1184-byte encapsulation key plus the 1088-byte ciphertext, both from NIST FIPS 203. The last row is what our entire architecture rests on, and it is now a measured fact rather than an opinion.

Steps 3 and 4 — how long does anything take?

The script encrypts the same reading 5000 times and times each one, then does the same for decryption. A single measurement would be noise — the machine might pause for a background update in the middle of it.

We report the median rather than only the average, because an average is wrecked by outliers: if one run in five thousand takes 50 ms because the operating system had other ideas, the mean jumps and the median does not. The p95 figure — “95% of runs were faster than this” — gives the realistic worst case.

End-to-end latency is measured differently: connect to the gateway as a device would, start a stopwatch, send one reading, then ask the cloud’s API every 5 ms whether it has that reading yet, and stop the clock when it does. Twenty samples.

MeasurementMedianMeaning
Encrypt one frame0.0058 msabout 172,000 per second
Decrypt one frame0.0059 msabout 169,000 per second
Device → cloud, end to end9.7 ms33.5 ms at p95

An honest limitation, recorded in the output file: because we poll every 5 ms, a reading that arrived at 6 ms might not be noticed until 10 ms. So 9.7 ms is an upper bound. That is acceptable because the identical method runs after ML-KEM integration, so the same overhead sits in both numbers and cancels out of the comparison. Stating the limits of your own instrument is part of the work, not an admission.

Putting the two together is where it gets useful: encryption accounts for 0.0117 ms of that 9.7 ms, roughly 0.1%. The remaining 99.9% is networking, HTTP and Python. The cipher is not the cost — and now we can prove it, which stops us wrongly blaming ML-KEM later for slowness the old system already had.

Step 5 — how much can the system take?

Send 200 readings back to back on one connection, watch the cloud’s stored count until it stops rising, and divide. Result: 105.5 readings per second through the whole chain.

One device reporting every two seconds produces 0.5 readings per second, so a single gateway could carry roughly 210 devices. That is a capacity estimate derived from a measurement rather than guessed — and if ML-KEM drops throughput to 80/s, we will be able to say capacity fell to about 160 devices per gateway, which is exactly the kind of operational statement the brief is looking for.

Step 6 — saved, dated, citable

Everything is written to docs/measurements/baseline-2026-09-17.json together with the date, Python version and platform. Numbers printed to a terminal are gone by the time the report is due in October, and recording the environment means somebody else can reproduce the run.

How we use it after ML-KEM

Same script, one extra flag — python -m tools.baseline --e2e --label mlkem — which writes a second file alongside the first. Then the report’s central table builds itself:

MeasurementBeforeAfter

Notice the shape of that table: the top half will get worse and the bottom half gets better. That trade-off is the report. “We accepted X milliseconds and Y bytes in exchange for key establishment that survives a quantum computer” is a real engineering argument. Without a baseline we could claim the benefit but never price it.

What the baseline already tells us

  1. The old cryptography is fast because it does nothing. A zero-byte handshake is zero security in key establishment, not an achievement.
  2. Per-message encryption is effectively free — about six microseconds, 0.1% of end-to-end time. So the migration’s cost will land in setup, not in every message, which means it amortises across the thousands of readings that follow each handshake.
  3. ML-KEM cannot run on the device. 1184 bytes against a 256-byte buffer. Measured, not asserted — and that is what justifies terminating post-quantum cryptography at the gateway.
  4. The bottleneck is the pipeline, not the cipher. If we need more capacity later, the work is in the HTTP forwarding, not the cryptography.

Post-quantum observability — the requirement most groups will miss

The brief asks for “post-quantum-related observability”, which means metrics about the migration itself:

  • Handshakes by suite — watch the rollout progress live
  • Handshake latency, classical versus ML-KEM — the performance cost, measured rather than asserted
  • A downgrade counter — if this rises, something is forcing peers back onto weak cryptography, possibly an attack
  • Key and ciphertext sizes — the bandwidth cost of post-quantum crypto

Together those answer the question a real security officer actually asks: how far along is our post-quantum migration, and is anything going wrong?

Where the marks actually come from

This is the section to read twice, because it is the one most groups get wrong.

The core instruction

The purpose is not to demonstrate that the LLM produced perfect code, but to demonstrate that the group can assess, validate, improve, and take responsibility for AI-assisted software development.SDMO project brief §1
A solution that runs successfully is not necessarily correct, secure, maintainable, or suitable for operations.SDMO project brief §2

The rules, plainly

  1. We must use an LLM to generate the code. It is not optional.
  2. We must treat its output as untrusted — like code from a stranger on the internet.
  3. The real prompts go into the technical documentation.
  4. For every generated artifact: what we accepted, modified or rejected, and why.
  5. How each problem was found, and which risks remain.
  6. Part 3 reflections are written without AI, individually.

We already have a textbook example

The generated gateway code ran perfectly. Then we killed a device mid-stream and it crashed the handler thread with an unhandled traceback. That one incident is a complete evaluation entry:

Artifact
LLM-generated gateway connection handler
Symptom
Unhandled ConnectionResetError (WinError 10054) killing the handler thread
Trigger
A field device losing power instead of closing cleanly — a daily event in reality
Found by
Failure testing, not code review. Reading it would not have caught this.
Impact
Noisy tracebacks an on-call operator has to triage, plus a dead handler thread
Decision
Modified — catch OSError, log one clean operator-readable line
Fix
edge_gateway/gateway.py:96

Ten more of those across the project and Part 1 writes itself. Note the shape of it: the code worked, the demo would have passed, and it was still wrong.

What to look for in generated code

  1. Does it handle failure, or only the happy path?
  2. Does it call library functions that don’t exist?
  3. Is the cryptography genuinely appropriate, or merely plausible-looking?
  4. Are secrets hardcoded?
  5. Does it validate its inputs?
  6. Is it thread-safe, given it runs concurrently?
  7. Will we understand it in six weeks?
  8. Are the error messages useful to an operator?

One warning worth writing down now

The library we plan to use, kyber-py, is pure Python and explicitly not constant-time. Do not hide that. “We chose a non-production library for an educational integration; here is the timing side-channel risk we accept, and here is how liboqs would remove it” is exactly the critical evaluation the brief rewards.
